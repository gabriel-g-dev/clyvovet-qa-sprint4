# CT22 — .NET distingue liveness e readiness de Oracle e MongoDB

**Objetivo:** Verificar liveness e readiness reais dos dois providers, sem interromper serviços compartilhados.

**Azure:** [CT22 · #84](https://dev.azure.com/clyvovet-fiap-2026-rm563298/ClyvoVet/_workitems/edit/84) · [PBI #28](https://dev.azure.com/clyvovet-fiap-2026-rm563298/ClyvoVet/_workitems/edit/28). Origem: Sprint 3; regressão do release na Sprint 4.

**Pré-condições:** API .NET no commit e80bfc05e203944054c4ab3f43eb4e6f5a098426, SDK 9; origem http://localhost:5109. Usar Oracle 21 com schema exclusivo e migration 20261025155040_OracleBaseline aplicada previamente, conforme README da versão fixada; não aplicar scripts legados ou migrations em banco compartilhado. MongoDB de QA disponível em banco descartável próprio. Configurar somente na sessão ConnectionStrings__OracleConnection, Mongo__ConnectionString e Mongo__DatabaseName. Credenciais sintéticas exclusivas desse ambiente: Auth__Username=qa-admin, Auth__Password=QaLocal123!, Auth__SigningKey=QaOnlySigningKey_ClyvoVet_2026_32_chars. Não são credenciais de produção. POST /api/auth/login devolve accessToken e tokenType=Bearer; todas as rotas de negócio exigem Authorization: Bearer `<accessToken>` com scope=clinical. Usar Content-Type application/json. Não registrar tokens, chave real ou connection strings nas evidências. Registrar D em UTC e calcular D-1/D+30 antes de iniciar. Capturar IDs das respostas; request de pet usa tutorId, resposta usa donoId. As listagens principais são paginadas em data/page/pageSize/totalItems/totalPages; não confundir com os arrays das rotas adicionais.

**Entradas controladas:** Containers próprios de Oracle e MongoDB; GET /health/live e /health/ready; X-Correlation-Id: QA-CT22. Interromper e restaurar um banco de cada vez, com ambos saudáveis no início.

**Saída esperada:** Ambos disponíveis: live e ready=200 Healthy. Oracle indisponível ou Mongo indisponível: live=200 e ready=503 Unhealthy. JSON contém correlationId=QA-CT22, totalDurationMs e checks oracle/mongo com durações não negativas e sem connection string ou stack trace. Após restauração, ready=200.

| Passo | Procedimento | Resultado esperado |
|---:|---|---|
| 1 | Com os dois bancos QA saudáveis chamar /health/live e /health/ready usando X-Correlation-Id: QA-CT22. | 200 Healthy em ambas; readiness contém checks oracle e mongo Healthy, correlationId=QA-CT22 e durações não negativas. |
| 2 | Parar apenas o container Oracle QA e repetir as duas chamadas até o health check terminar. | Liveness 200; readiness 503 Unhealthy, oracle Unhealthy e mongo Healthy; nenhuma credencial ou stack trace no corpo. |
| 3 | Restaurar Oracle e aguardar ready=200; parar apenas MongoDB QA e repetir as chamadas com o mesmo header. | Liveness 200; readiness 503, mongo Unhealthy e oracle Healthy; correlationId=QA-CT22, resposta sanitizada e durações não negativas. |
| 4 | Restaurar MongoDB e consultar readiness novamente, mantendo Oracle disponível. | Ready 200 Healthy; ambos os checks Healthy; serviços QA restaurados. |

**Aprovação:** Aprovar somente se todos os resultados de cada passo forem observados; qualquer divergência reprova o caso.

**Restauração:** Reiniciar os dois containers próprios interrompidos e confirmar readiness Healthy; não parar serviços compartilhados.
