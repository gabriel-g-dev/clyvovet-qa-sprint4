# CT22 — .NET separa liveness e readiness na indisponibilidade do Oracle

IDENTIFICAÇÃO: CT22 — .NET separa liveness e readiness na indisponibilidade do Oracle

OBJETIVO: Verificar health checks reais sem derrubar ambiente compartilhado.

RASTREABILIDADE: PBI #28 (https://dev.azure.com/clyvovet-fiap-2026-rm563298/ClyvoVet/_workitems/edit/28). Funcionalidade planejada na Sprint 3; regressão/validação no release Sprint 4, entrega 04/11/2026.

PRÉ-CONDIÇÕES: .NET no commit 83b6dd7, SDK 9 e Oracle de QA vazio com script_bd.sql aplicado; API http://localhost:5109. Configurar Auth__Username=qa-admin, Auth__Password=QaLocal123!, Auth__SigningKey com chave exclusiva de teste de pelo menos 32 caracteres; connection string somente no ambiente. Nunca usar Oracle de produção. A interrupção só pode ocorrer em container descartável de propriedade do executor.

ENTRADAS CONTROLADAS: Oracle de QA em container próprio; GET /health/live e /health/ready; X-Correlation-Id: QA-CT22; interrupção e restauração apenas desse Oracle

SAÍDA ESPERADA: Com banco disponível: live=200 Healthy e ready=200 Healthy; banco parado: live=200 e ready=503 Unhealthy sem connection string/stack trace; após restaurar banco: ready=200.

PASSOS:
1. Com Oracle QA saudável chamar /health/live e /health/ready com X-Correlation-Id QA-CT22.
   Esperado: 200 Healthy em ambas; JSON de readiness inclui check oracle e duração.
2. Parar somente o container Oracle de QA; repetir as duas requisições.
   Esperado: Liveness 200; readiness 503 Unhealthy, retorno sem credenciais nem stack trace.
3. Conferir headers e corpo.
   Esperado: Correlation ID QA-CT22 presente; durações não negativas; descrição genérica.
4. Reiniciar o Oracle QA e aguardar conectividade; repetir readiness.
   Esperado: 200 Healthy; serviço restaurado.

CRITÉRIO DE APROVAÇÃO: Aprovar somente se todos os resultados de cada passo forem observados; qualquer divergência reprova o caso.

RESTAURAÇÃO: Remover apenas os registros QA criados no ambiente de teste; restaurar os serviços interrompidos.

EXECUÇÃO: Planejado. Execução manual não realizada. Resultados da automação, quando disponíveis, são evidências separadas.

OBSERVAÇÕES: Relacionado também ao PBI 34 da Sprint 4. Testes de integração existentes usam SQLite, o que não comprova execução Docker/Oracle.
