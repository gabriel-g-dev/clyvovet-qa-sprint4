OBJETIVO: Verificar contrato HTTP de manutenção e leitura do registro clínico.

RASTREABILIDADE: PBI #16 (https://dev.azure.com/clyvovet-fiap-2026-rm563298/ClyvoVet/_workitems/edit/16). Funcionalidade planejada na Sprint 1; regressão/validação no release Sprint 4, entrega 04/11/2026.

PRÉ-CONDIÇÕES: .NET no commit 83b6dd7, SDK 9 e Oracle de QA vazio com script_bd.sql aplicado; API http://localhost:5109. Configurar Auth__Username=qa-admin, Auth__Password=QaLocal123!, Auth__SigningKey=QaOnlySigningKey_ClyvoVet_2026_32_chars (valor público exclusivo do QA); connection string somente no ambiente. Nunca usar Oracle de produção. JSON com Content-Type application/json. O login devolve accessToken e tokenType=Bearer; guardar accessToken somente no cliente e usá-lo no header Authorization. O projeto não compartilha autenticação com Java.

ENTRADAS CONTROLADAS: Login username=qa-admin,password=QaLocal123!; tutor nome=Tutor QA20,email=qa20@example.test,telefone=(11)90000-0020; pet QA-NET20,Cachorro,SRD,2023-01-15T00:00:00,peso=12.5,tutorId=idTutor; nome editado QA-NET20-editado

SAÍDA ESPERADA: Login=200 com accessToken não vazio e tokenType=Bearer; POST sem token=401; POST tutor e pet autenticados=201 com Location; GET do pet com consultas/vacinas vazias; PUT=200; DELETE=204; GET posterior=404 ProblemDetails.

PASSOS:
1. POST /api/auth/login com credenciais indicadas; guardar token.
   Esperado: 200 com accessToken não vazio e tokenType=Bearer; guardar accessToken para Authorization: Bearer <accessToken>.
2. POST /api/pets com corpo válido, mas sem token.
   Esperado: 401; nenhuma escrita realizada.
3. Com token criar tutor em /api/tutores e pet em /api/pets usando idTutor retornado.
   Esperado: 201 em ambas; Location do pet resolve para o id criado.
4. GET do pet e PUT nome QA-NET20-editado, demais campos iguais.
   Esperado: GET 200 com histórico vazio; PUT 200 e GET posterior confirma novo nome.
5. DELETE pet, depois tutor; GET do pet excluído.
   Esperado: 204 nas exclusões; GET 404 com status=404 no ProblemDetails.

CRITÉRIO DE APROVAÇÃO: Aprovar somente se todos os resultados de cada passo forem observados; qualquer divergência reprova o caso.

RESTAURAÇÃO: Remover apenas os registros QA criados no ambiente de teste; restaurar os serviços interrompidos.

EXECUÇÃO: Planejado. Execução manual não realizada. Resultados da automação, quando disponíveis, são evidências separadas.

OBSERVAÇÕES: A configuração de autenticação .NET é própria e não possui os perfis ADMIN/TUTOR do Java. Não pressupor JWT compartilhado entre backends.
